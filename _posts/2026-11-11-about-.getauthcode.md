# WeLink `HWH5.getAuthCode` 调查总结


**目标程序**：WeLink（Electron 桌面客户端）
`C:\Program Files (x86)\WeLink\WeLink.exe`，sha256 `e744c698…`


**调查目的**：搞清楚 `HWH5.getAuthCode()` 端到端怎么工作（网页接口 → 桥 → 宿主 → 服务端），以及这张"授权码"到底从哪来、由谁签发，从而为自己应用设计一套等价实现。


**约束**：以静态分析为主；只在用户明确同意后运行过一次程序；不复制专有代码；**不记录任何真实凭据值**（本文所有涉及凭据的地方只写长度和形状）。


---


## 一、一句话结论


`HWH5.getAuthCode()` 不是"计算出"一张码，而是**向服务端要**一张码：网页侧只是一个请求/回调的薄壳，宿主进程收到请求后去打一个 SSO 接口取票，再把票原样递回页面。**码由服务端签发，客户端只做中转，且每次调用都新签一张不同的票。**


---


## 二、调查做了什么


| 阶段 | 动作 | 结果 |
|---|---|---|
| 1 | 识别程序类型 | Electron 外壳 + 大量原生 DLL；网页代码在 `app.asar` 与 `plugin/business` 内的 zip 里 |
| 2 | 解包并定位网页 SDK | `hwh5.js`（268 KB）、`wecodeJsapiSdk.js`（1.07 MB）、`preload.js`、`api_mapping.json` |
| 3 | 静态追链路 | 逐跳定位到宿主处理者与服务端接口（见第三节） |
| 4 | 尝试运行观察 | 首次尝试失败（调试端口被 Electron 保险丝关闭，`fnd_13`） |
| 5 | 改用日志取证 | 读取客户端自身日志，得到登录时序、隧道时序、请求记录 |
| 6 | 用户打开一个 WeCode 小程序 | **完整调用链在运行日志中逐条出现**，取得真实响应形状 |
| 7 | 本地比对两张票 | 两次调用得到的票**不同**，确认逐次签发 |


> 说明：第 6 步由用户手动操作触发；第 7 步的比较由用户在本机执行，只报告了"相同/不同"的结论，值未离开本机。

## 三、完整调用链（静态 + 实测一致）


### 3.1 逐跳路径


```
① 页面 JS
   HWH5.getAuthCode({ clientId })              // clientId = 第三方应用注册的 appid
      ↓  通用信封
② HWH5.callMethod(JSON.stringify({
        funcName: "getAuthCode", data: {clientId}, callbackId }))
      ↓  Electron webview 通道
③ preload.js
   ipcRenderer.sendToHost("preload:getAuthCode")
      ↓
④ 宿主页面（wecodeJsapiSdk.js）
   webview.on("ipc-message") → getChannelMap()["preload:getAuthCode"]
      → this.getAuthCode(winId)
      ↓  一次服务端调用
⑤ POST https://{middleEndAddress}/mcloud/mag/ProxyForText/ssoauth/v1/code
      （GET_PUBLIC_NOURL_CODE，无请求体，带 getAuthHeader() 的会话头）
      ↓
⑥ r = recv_body.code || ""          // 空则记错误并回空串
      ↓
⑦ webContents.send("preload:authCode", r)
      ↓
⑧ 页面回调 HWH5.callbackNative(JSON.stringify({
        callbackId, data: base64(UTF-8 JSON) }))
   → 按 callbackId 配对，回调收到 { code }
```

## 四、这张"票"的事实


| 项目 | 结论 | 依据 |
|---|---|---|
| 形状 | **96 位大写十六进制字符**（= 48 字节） | `fnd_38` |
| 外壳 | **裸值**，无包裹对象；`result=1` 表示成功，`message=undefined` | `fnd_38` |
| 是否告知寿命 | **否**。响应里没有任何过期字段 | `fnd_41` |
| 是否逐次签发 | **是**。相隔约 11 秒的两次调用值不同 | `fnd_42` |
| 客户端是否缓存 | **否**。处理者每次现取，无 memo | `fnd_40` |
| 客户端是否兑换 | **否**。两个 SDK 里都没有针对这张票的兑换代码 | `fnd_40` |
| 兑换地点 | **小程序自己的后端，服务端到服务端** | `fnd_40` |
| 往返耗时 | 423 ms（含原生 HTTP 栈首次加载开销） | `fnd_38` |


### 4.1 一个对照，说明设计意图


同一个 SDK 里，第三方应用换到的 **JWT 是带寿命的，而且被认真执行**（`fnd_41`）：


```
缓存在 welink_roma_auth_<appid>：{ time, jwt }
判过期：  time + 1000 * parseInt(jwt.expire_in) < Date.now()  → 重新获取
```


而这张 auth code **什么字段都不给**。差别不是疏漏，是态度：**票就是给你立刻用掉的。**


### 4.2 两种"码"不要混


| 用途 | 端点 | 返回读取方式 |
|---|---|---|
| H5 页面取票（本文主题） | `POST …/ssoauth/v1/code` | 读 `recv_body.code` |
| WeCode 专用 | `POST …/sso/auth/v2/code` | 要求 `code === "0"`，读 `recv_body.auth_code` |
| 免登录跳转 | `getExemptionCode` → `https://login.<host>/sso/auth/v1/code/session?code=…&targetUrl=…` | — |
| 第三方换 JWT | `POST {该应用自己的域名}/jwt/token`，体 `{appid, sso:"welink", token}` | 读 `access_token` / `token_type` |

## 五、身份与会话从哪来


- 所有能力调用都走同一个代理主机：`https://{middleEndAddress}/mcloud/mag/ProxyForText/…`，实测主机为 `https://api.welink.huaweicloud.com`（`fnd_16`）。
- 请求头由 `getAuthHeader()` 生成，其内容来自原生层的一次方法调用（`fnd_19`、`fnd_20`）：


```
getAuthorizationInfo():
    { middle_ground_onebox_cookie, middle_ground_token }
       = Pedestal.callMethod("method://pedestal/getCurrLoginStatus", { entry: "headers" })


getAuthHeader():
    if (window.isRedblue) return { Cookie }
    return { Cookie: "token=" + token, "x-wlk-Authorization": token }
```


- `getCurrLoginStatus` 是**按需调用**，没有定时器；唯一刷新机制是 401 → `refreshMiddleGroundToken()`（`fnd_26`）。
- **token 会直接交给页面 JS**（`fnd_19`）。这是一个客观存在的暴露面。


### 5.1 登录一次，拿到全部地址


登录成功那一条日志等于一份完整会话说明书（`fnd_35`）：


```

## 六、TUP / 隧道 与这张票的真实关系


这是本次最容易误解的一点，结论明确：


### 6.1 票不经过隧道；隧道反而需要票


`pedestal/wk_login.log` 的时间顺序（`fnd_34`）：


| 时刻 | 事件 |
|---|---|
| 22:51:00.703 | `loginStatus = 0`，`middleGroundToken.len = 0`，`maaUri` 为空 |
| **22:51:09.069** | `loginStatus = 2`，`middleGroundToken.len = 36`，`maaUri = im.welink.huaweicloud.com:443` |
| 22:51:09.941 | IM 侧 `authToken.len = 36` → `need login` |
| 22:51:10.013 | 隧道才开始 TLS 握手 |
| 22:51:10.181 | 隧道发出登录请求 |


**token 比隧道的第一条连接早将近 1 秒**，且隧道登录本身要用这个 token → **通道不可能产出它。**


### 6.2 取票也不走隧道


取票那一步加载的是 `http_with_rs.dll`（普通 HTTPS 栈），与 IM 长连接无关（`fnd_38`）。


### 6.3 TUP 的两种"面孔"不要混


| | 载体 | 通道 |
|---|---|---|
| TUP HTTP 接口 | TUP 库 | **普通 HTTPS**（登录、业务、取票都走这里） |
| TUP 长连接（隧道） | TUP | 私有协议，目标为 `maaUri` |


"经过 TUP" ≠ "经过私有隧道"。


### 6.4 隧道自身的传输安全（客观测量）


| 项目 | 结论 | 依据 |
|---|---|---|
| 证书校验 | **开启**：`should_verify = 1` | `fnd_30` |
| 实际校验链 | `*.welink.huaweicloud.com` → GlobalSign RSA OV SSL CA 2018 → GlobalSign Root CA - R3，逐级 `preverified success` | `fnd_30` |
| 信任库 | **自带** OpenSSL 哈希式证书目录，**不认 Windows 证书库**（装企业根证书拦不住它） | `fnd_31` |
| 协议栈 | 静态链接 OpenSSL 3.0.16，版本表含 TLS 1.3/1.2/1.1/1.0 与 DTLS/QUIC | `fnd_31` |
| 载荷加密 | **只有 TLS 一层**（未发现应用层加密迹象） | `fnd_33` |
| 信任库卫生 | 目录内有一份自签 CA（`CN=www.example.com`，O=Huawei，有效期至 2099，CA:TRUE，注释指向交换机产品线），**是否被加载未证** | `fnd_32`、`unk_68b136…` |


**评价**：在"防窃听、防假冒服务器"这件事上，这一层做得实在；但它**不提供任何"客户端可信"的保证**，那从来不是它的职责。

## 七、客户端加固与暴露面


### 7.1 已做的加固


- Electron 保险丝：`EnableNodeCliInspectArguments` **关闭**（`--inspect` 无效），`OnlyLoadAppFromAsar` 开启（`fnd_13`）。
  **实测后果**：三次尝试附加调试端口全部 connection refused，运行观察只能改走日志。
- API 分级：`getAuthCode` 被归入"服务授权"而非通用能力（`fnd_8`）；调用前过权限表与风控名单，实测 `openCheck:true` 生效（`fnd_37`）。
- 传输：自带根证书，不信任操作系统证书库（`fnd_31`）。


### 7.2 客观存在的暴露面


| 暴露面 | 事实 | 依据 |
|---|---|---|
| 凭据明文落盘 | 取票响应把票**原样写进日志**，而同一个日志里 URL 却被 35 个 `*` 打码 | `fnd_39` |
| 票新鲜且先到先得 | 每调一次新签一张，落在日志里的票都处于寿命开头 | `fnd_42` |
| token 交给页面 | `getAuthHeader()` 把会话 token 返回给页面 JS | `fnd_19` |
| 会话无绑定证据 | 未见 nonce / deviceId / 请求签名；会话为长寿命 bearer | `fnd_24` |
| 日志信息量大 | 设备名、IP、证书主题、连接五元组、重试参数均明文 | `fnd_28` |


**注**：以上只陈述观察到的现象，不构成对漏洞的断言；"没看到"不等于"不存在"。

## 八、验证矩阵


### 已证明（观察）


- 完整调用链存在且顺序与静态分析一致（`fnd_37`）
- 票为 96 位大写十六进制裸值（`fnd_38`）
- 每次调用新签一张，值不同（`fnd_42`，来自用户本机比对）
- 取票走普通 HTTPS，不经隧道（`fnd_38`）
- token 早于隧道建立，隧道登录依赖 token（`fnd_34`）
- 隧道 TLS 校验开启且链路完整（`fnd_30`）
- 客户端使用自带 CA 目录（`fnd_31`）
- 凭据明文写入日志而 URL 被打码（`fnd_39`）


### 推论（由观察算出）


- 票由服务端签发，客户端无法自造（`fnd_9`、`fnd_40`）
- 票的设计意图是"立即使用"（无过期字段 + 逐次签发 + 无缓存）
- 因为信任边界在服务端，客户端"不设防"才成立；这与传输层是否牢固是两件事


### 未知


| 编号 | 内容 | 状态 | 如何关闭 |
|---|---|---|---|
| `unk_63ffb4…` | 票的**确切寿命**、是否**一次性** | blocked | 用自己在自有租户注册的 appid 做少量兑换测试；或查厂商文档。**不要拿日志里的票打生产鉴权** |

## 九、对复刻的可用结论


### 9.1 设计原则（从证据反推）


1. **票只由服务端签发**，客户端每一侧都无权自造。
2. **客户端不缓存**，每次现取——简化了失效处理，也缩短了重放窗口。
3. **不告知寿命**，语义上等于"立刻用"。
4. **兑换只发生在服务端之间**，浏览器永不做兑换。
5. **票绑定"请求它的那个 clientId"**，而不是绑定某张长期会话。


### 9.2 建议规格


```
POST /auth/v1/code
  入参   { clientId }                    // 应用注册 id，必填
  出参   { code }                        // 不透明，不给 expire_in
  规则   60 秒有效 / 一次性 / 绑定 clientId + 当前会话
  限制   每个 clientId 每分钟限量，防批量铸票


POST /auth/v1/token                     // 仅服务端到服务端
  入参   { appId, sso: "sso", code }
  出参   { access_token, token_type, expire_in }
  规则   兑换即作废；同一 code 二次兑换返回明确错误
```


### 9.3 参考实现骨架（伪代码）


**主进程（Node / Electron main）**


```js
ipcMain.handle("auth:code", async (event, { clientId }) => {
  if (typeof clientId !== "string" || !clientId) throw new Error("bad clientId");
  if (!session.isLoggedIn(event.senderFrame)) throw new Error("not signed in");
  if (!rateLimit.take(clientId))            throw new Error("rate limited");


  const r = await fetch(`${cfg.baseUrl}/auth/v1/code`, {
    method: "POST",
    headers: { "Content-Type": "application/json", ...session.headers() },
    body: JSON.stringify({ clientId }),
  });
  if (!r.ok) throw new Error(`auth code failed: ${r.status}`);
  const { code } = await r.json();
  if (!code) throw new Error("empty code");


  log.info("auth code issued", { clientId, len: code.length }); // 只记元数据
  return { code };
});
```


**渲染进程 / preload（窄接口，页面拿不到会话）**


```js
contextBridge.exposeInMainWorld("Auth", {
  getAuthCode: (clientId) => ipcRenderer.invoke("auth:code", { clientId }),
});
```


### 9.4 与 WeLink 的关键差异（建议之处）


| 项目 | WeLink 做法 | 建议做法 |
|---|---|---|
| 会话 token 给页面 | 给（`getAuthHeader` 返回 token） | **不给**，只在主进程持有 |
| 凭据进日志 | 明文（`fnd_39`） | **只记长度/长度区间**，或哈希前 8 位 |
| 票寿命告知 | 不告知 | 可在服务端记录以便审计，仍不返回给客户端 |
| 兑换位置 | 服务端之间 | 同（保持不变，这是正确做法） |
| 设备绑定 | 未见证据 | 加 nonce 或设备指纹，至少对高风险接口 |
